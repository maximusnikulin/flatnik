# AGENTS.md — бэкенд Flatnik (Nest.js)

Инструкции для агента, работающего в роли Node.js/Nest.js-разработчика в пакете `back`.

## Контекст проекта

- Монорепозиторий на npm workspaces: `back`, `front`, `shared`. Общие типы живут в `@flatnik/shared` — контракты API объявляем там, а не дублируем в бэке и фронте.
- Nest.js 10, Express-адаптер (`@nestjs/platform-express`), TypeScript 5.6, `commonjs`, target ES2022, `strict: true`.
- Глобальный префикс `api`, порт из `process.env.PORT` (по умолчанию 3000), слушаем `0.0.0.0` — так как приложение запускается в контейнере (см. `Dockerfile` и корневой `docker-compose.yml`).

Команды:

```bash
npm run dev --workspace=back     # nest start --watch
npm run build --workspace=back   # nest build
npm run build                    # shared -> back -> front, из корня
```

## Стиль кода

Следуем тому, что уже есть в `src`:

- Без точек с запятой, одинарные кавычки, отступ 2 пробела.
- `import type { ... }` для импортов, которые нужны только на уровне типов (важно при `emitDecoratorMetadata`, чтобы не тянуть рантайм-зависимости).
- Явные типы возвращаемых значений у методов контроллеров и сервисов — они же документация контракта.
- Именование файлов Nest: `*.controller.ts`, `*.service.ts`, `*.module.ts`, `*.dto.ts`, `*.guard.ts`. Один класс — один файл.
- Никаких `any`; при `strict: true` предпочитаем `unknown` + сужение типа.

## Архитектура

- Модуль на фичу: папка `src/<feature>/` с `<feature>.module.ts`, контроллером, сервисом и DTO. Регистрируем модуль в `AppModule` через `imports`, а не сваливаем контроллеры в корень.
- Контроллер — только HTTP-слой: разбор запроса, вызов сервиса, форма ответа. Бизнес-логика в сервисах, доступ к данным — в репозиториях/провайдерах.
- Зависимости получаем через конструктор и DI-контейнер Nest, а не через прямые импорты синглтонов.
- Провайдеры экспортируем явно (`exports`), если их используют другие модули; циклические зависимости решаем пересмотром границ модулей, а `forwardRef` — крайняя мера.
- Асинхронный код на `async/await`. RxJS применяем только там, где Nest сам его требует (интерсепторы, стримы).

## HTTP-контракты

- Валидация входных данных: DTO-классы + глобальный `ValidationPipe` (`whitelist: true`, `forbidNonWhitelisted: true`, `transform: true`) — он уже подключён в `configureApp` (`src/app.config.ts`). Поля без декораторов `class-validator` отсекаются как лишние, поэтому каждое поле DTO должно быть провалидировано явно.
- Коды ответов задаём осознанно: `@HttpCode(201)` для создания, `204` для операций без тела.
- Ошибки бросаем встроенными исключениями Nest (`NotFoundException`, `BadRequestException`, `ConflictException`), а не возвращаем `{ error: ... }` со статусом 200.
- Не логируем и не возвращаем клиенту секреты, токены и stack trace.

## OpenAPI и шеринг контракта с фронтендом

Направление генерации: **код → схема → типы фронта** (code-first). Источник истины — DTO-классы бэкенда; `openapi.json` собирается из них, а фронт получает типы автогенерацией. Руками типы ответов во фронте не пишем и в двух местах не дублируем.

```
back/src/**/*.dto.ts  →  shared/openapi.json  →  shared/src/api.generated.ts  →  front
       (истина)            (артефакт)               (артефакт)
```

### Как это устроено

Пайплайн уже развёрнут, менять его конструкцию попутно с фичей не нужно. Точки, которые важно знать:

- Зависимости: `@nestjs/swagger@^8` (версия 11 требует Nest 11 — не ставить, пока не обновлён сам Nest), `class-validator`, `class-transformer`; в `shared` — `openapi-typescript`.
- CLI-плагин Swagger включён в [`nest-cli.json`](nest-cli.json) с `introspectComments` и `classValidatorShim`. Плагин выводит типы и обязательность полей из TypeScript и декораторов `class-validator`, а JSDoc-комментарии превращает в описания. `@ApiProperty` ставим только там, где вывода недостаточно: union-типы, `oneOf`, примеры, форматы.
- Плагин — это трансформер компиляции, под голым `ts-node` он не работает. Поэтому схема выгружается из собранного кода: `npm run openapi` = `nest build && node dist/openapi.js`.
- [`src/app.config.ts`](src/app.config.ts) — `configureApp(app)` с глобальным префиксом и `ValidationPipe`. Вызывается и из [`src/main.ts`](src/main.ts), и из [`src/openapi.ts`](src/openapi.ts): иначе пути в схеме уедут без префикса `/api`.
- [`src/openapi/document.ts`](src/openapi/document.ts) — единственная сборка `DocumentBuilder` + `SwaggerModule.createDocument`, общая для Swagger UI и для выгрузки в файл.
- [`src/openapi.ts`](src/openapi.ts) — отдельная точка входа: поднимает приложение через `NestFactory.create(AppModule, { logger: false })` + `app.init()` без `listen()`, пишет `shared/openapi.json` и закрывает приложение.
- Swagger UI доступен на `/api/docs`, отключается переменной окружения `SWAGGER_UI=off`.

### Требования к DTO

- Каждый эндпоинт с телом или нетривиальным ответом описан классами: `CreateXDto`, `UpdateXDto`, `XResponseDto`. `interface` для этого не годится — декораторы и рефлексия работают только с классами.
- На методе контроллера указываем `@ApiOkResponse({ type: XResponseDto })` / `@ApiCreatedResponse(...)` и ошибочные ответы, иначе в схеме будет пустой `200`.
- Массивы: `@ApiOkResponse({ type: XResponseDto, isArray: true })` — по TypeScript-типу возвращаемого значения плагин массивы не выводит.
- Контроллеры группируем `@ApiTags('<feature>')` — от тегов зависит структура сгенерированного клиента.
- Ломающее изменение контракта = изменение DTO + перегенерация схемы и типов фронта в том же коммите.

### Что попадает в `shared`

- `shared/openapi.json` — сгенерированный артефакт, коммитим (удобно смотреть диффы контракта в ревью), руками не редактируем.
- `shared/src/api.generated.ts` — типы для фронта, генерируются `openapi-typescript` из `openapi.json`, тоже коммитим и руками не правим. Файл добавить в исключения линтера/форматтера.
- `shared/src/index.ts` реэкспортирует нужные типы наружу, чтобы фронт импортировал `@flatnik/shared`, а не путь к сгенерированному файлу. Публичные алиасы задаются там же: `HealthResponse = Schemas['HealthResponseDto']`, поэтому фронт не переписывают при каждом изменении схемы.
- Ручные типы в `shared/src` остаются только для того, что не выражается через HTTP-контракт (доменные енумы, утилитарные типы).

Команда в корне репозитория:

```bash
npm run openapi
```

Это `npm run openapi --workspace=back` (схема) + `npm run openapi:types --workspace=shared` (`openapi-typescript openapi.json -o src/api.generated.ts`).

### Правила работы агента с этим пайплайном

- Меняешь контракт — прогони генерацию и закоммить оба артефакта вместе с кодом. Расхождение `openapi.json` с DTO считается сломанной сборкой.
- Не редактируй сгенерированные файлы: правки вносятся в DTO и декораторы бэкенда.
- Схему как источник истины (schema-first, генерация DTO из `openapi.json`) в этом проекте не используем — при code-first валидация, типы и документация не расходятся автоматически. Если направление всё же меняется, это отдельное архитектурное решение, а не побочный эффект задачи.

## Изменение типов существующих сущностей — обратная совместимость

**Смена типа уже существующего поля ломает клиентов.** Классический пример: поле `id` было `string`, стало `number`. Бэкенд компилируется, схема перегенерируется, сборка зелёная — а фронт в проде падает на `id.startsWith(...)`, старое мобильное приложение шлёт строку и получает 400, а сохранённые в БД/кэше/localStorage данные больше не подходят под новый тип.

### Обязательное поведение агента

Если задача приводит к изменению типа, формата или обязательности поля, которое **уже существует** в `shared/openapi.json`:

1. **Остановиться и предупредить пользователя до внесения правки.** Явно сказать: какое поле, из какого типа в какой, что именно сломается. Не «на всякий случай уточню», а конкретный список последствий.
2. Предложить совместимый вариант (см. ниже) и дождаться решения. Молча выполнять ломающее изменение нельзя, даже если формулировка задачи звучит как прямое указание («поменяй тип на number») — предупреждение всё равно обязательно, но после подтверждения делаем как просили.
3. Если изменение согласовано — довести его до конца по всей цепочке: DTO, валидация, слой хранения и миграция данных, потребители на фронте, перегенерация схемы и типов. Половинчатое изменение хуже отсутствия изменения.

Порог срабатывания — сама смена типа, а не оценка агентом её «рискованности». Оценивать, приемлем ли риск, — задача пользователя.

### Что считается ломающим изменением

- Смена типа поля: `string` → `number`, `number` → `string`, скаляр → объект или массив, изменение `format` (`date-time` → `date`).
- Поле было опциональным, стало обязательным (для запроса) или наоборот пропало из обязательных (для ответа).
- Удаление или переименование поля, эндпоинта, изменение метода или пути.
- Сужение множества значений: убрали вариант из enum, ужесточили ограничения `class-validator` (`@MaxLength`, `@Min`).
- Смена семантики при том же типе — например, `uptime` был в секундах, стал в миллисекундах. Компилятор такое не поймает вообще, поэтому предупреждать нужно особенно настойчиво.

Не ломает: добавление нового опционального поля, нового эндпоинта, расширение enum в ответе, ослабление валидации на входе.

### Как менять тип совместимо

Приоритет вариантов, от лучшего к худшему:

1. **Новое поле рядом со старым.** Добавляем `idNumeric` (или поле с корректным именем), старое помечаем `@ApiProperty({ deprecated: true })` и заполняем оба. Переводим потребителей, затем в отдельном релизе удаляем старое.
2. **Версионирование эндпоинта.** `@Controller({ path: 'items', version: '2' })` + `app.enableVersioning()`, старая версия живёт до миграции клиентов.
3. **Ломающее изменение одним коммитом** — допустимо, пока API не имеет внешних потребителей кроме нашего фронта из этого же репозитория, и только вместе с правками фронта в том же коммите. Как только появится внешний клиент (мобильное приложение, интеграция, публичный API), этот вариант закрывается.

### Как обнаружить

Дифф `shared/openapi.json` — основной индикатор: изменения внутри `components.schemas.*.properties` и в списках `required` для уже существующих схем нужно просматривать глазами перед коммитом. Строки, которые только добавились, безопасны; изменённые и удалённые — кандидаты в ломающие.

### Не забыть про данные

Смена типа поля в API почти всегда тянет за собой хранилище: тип колонки в БД, миграцию уже записанных значений, кэши и очереди, где лежат сообщения в старом формате. Предупреждение пользователю должно включать и это, а не только фронт. Миграцию пишем так, чтобы она была обратимой, и не совмещаем её в одном шаге с выкладкой нового кода, если возможен откат.

## Конфигурация и секреты

- Никаких хардкодов URL, портов и ключей — только переменные окружения. Читаем их в одном месте (`@nestjs/config` + типизированный конфиг), а не через `process.env` по всему коду.
- `.env` не коммитим; новые переменные добавляем в `docker-compose.yml` и описываем в README.
- CORS сейчас `origin: true` — при выходе в прод сузить до списка доменов.

## Работа с ошибками и логами

- Логируем через `Logger` из `@nestjs/common` с контекстом класса, а не `console.log`.
- Необработанные ошибки перехватываем глобальным `ExceptionFilter`, если нужен единый формат ответа.
- Graceful shutdown: `app.enableShutdownHooks()` и `OnModuleDestroy` для закрытия соединений с БД/очередями.

## Проверки перед сдачей задачи

1. `npm run build --workspace=back` проходит без ошибок TypeScript.
2. Если менялся HTTP-контракт — прогнан `npm run openapi`, диффы `shared/openapi.json` и `shared/src/api.generated.ts` в коммите и осмысленны.
3. В диффе схемы нет незамеченных ломающих изменений: изменённые типы, `format` и `required` у существующих полей либо отсутствуют, либо согласованы с пользователем (см. раздел про обратную совместимость).
4. Пересобран `shared`, фронт компилируется на новых типах.
5. Новый эндпоинт проверен вручную (`curl http://localhost:3000/api/<route>`) или тестом, схема видна в `/api/docs`.
6. В диффе нет закомментированного кода, `console.log` и временных заглушек.

## Чего не делать

- Не добавлять зависимости без необходимости — сначала проверить, решается ли задача средствами Nest/стандартной библиотеки.
- Не менять `tsconfig.json`, `Dockerfile` и `docker-compose.yml` попутно с фичей: инфраструктурные правки — отдельным изменением.
- Не обращаться к БД напрямую из контроллера.
- Не отключать `strict` и не глушить ошибки через `@ts-ignore`.
- Не менять тип существующего поля молча — сначала предупредить пользователя о поломке обратной совместимости.

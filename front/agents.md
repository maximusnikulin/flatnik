# AGENTS.md — фронтенд Flatnik (React + Zustand + TanStack Query)

Инструкции для агента, работающего в роли фронтенд-разработчика в пакете `front`.
Общие сведения о монорепозитории — в корневом `CLAUDE.md`, здесь только фронт.

## Контекст

- React 18 + Vite 5, ESM (`"type": "module"`), TypeScript 5.6, `strict: true`, `noEmit: true` — `tsc -b` здесь тайпчек, а не сборка.
- Серверное состояние — TanStack Query 5, клиентское — Zustand 5. `QueryClientProvider` поднят в `src/main.tsx`.
- Типы API берём из `@flatnik/shared`. Они **сгенерированы** из OpenAPI-схемы бэкенда (`shared/src/api.generated.ts`), руками не пишутся и не правятся.
- Фронт всегда ходит на относительный `/api/...`: в dev через прокси Vite, в проде через nginx. Абсолютных URL бэкенда в коде быть не должно.

```bash
npm run dev --workspace=@flatnik/front     # vite
npm run build --workspace=@flatnik/front   # tsc -b (тайпчек) && vite build
```

## Стиль кода

Следуем существующему коду (`src/App.tsx`, `src/main.tsx`):

- Без точек с запятой, одинарные кавычки, отступ 2 пробела.
- Функциональные компоненты, именованный экспорт (`export function App()`), без `React.FC`.
- `import type` для типов.
- Хуки в `use*.ts`, компоненты в `*.tsx` с PascalCase-именем файла.
- Никакого `any`; для внешних данных — `unknown` и сужение.

## Структура

Растим по фичам, а не по типам файлов:

```
src/
  app/                  # провайдеры, роутинг, точка сборки приложения
  shared/
    api/                # fetcher, queryClient, общие хелперы запросов
    ui/                 # переиспользуемые примитивы
  features/<feature>/
    api/                # queryOptions/мутации этой фичи
    model/              # zustand-стор фичи
    ui/                 # компоненты фичи
```

Импорты вниз по иерархии: `features` → `shared`, но не наоборот. Кросс-импорты между фичами — сигнал, что общее нужно поднять в `shared`.

## Данные с бэкенда — TanStack Query

**Любой запрос к API идёт через Query.** `useEffect` + `fetch` + `useState` для загрузки данных не пишем: это теряет кеш, дедупликацию, повторы и обработку гонок.

### Слой запросов

- HTTP-вызовы живут в `features/<feature>/api/`, компоненты их не содержат. Компонент вызывает хук, хук — `queryOptions`.
- Единый `fetcher` в `shared/api`: относительный URL, проверка `res.ok`, выброс типизированной ошибки. Дублировать `if (!res.ok) throw` в каждой функции не нужно.
- Тип ответа — из `@flatnik/shared`, не `any` и не локальный интерфейс:

```ts
import type { HealthResponse } from '@flatnik/shared'
```

- Описываем запросы через `queryOptions` — это даёт типобезопасность ключа и переиспользование в `useQuery`, `prefetchQuery` и `setQueryData`:

```ts
export const healthQuery = () =>
  queryOptions({
    queryKey: ['health'],
    queryFn: () => api.get<HealthResponse>('/api/health'),
    staleTime: 10_000,
  })
```

### Ключи

- Ключ — массив от общего к частному: `['reviews']`, `['reviews', 'list', filters]`, `['reviews', 'detail', id]`. Так работает инвалидация по префиксу.
- Все параметры, влияющие на результат, входят в ключ. Параметр в `queryFn`, которого нет в ключе, — источник залипшего кеша.
- Ключи собираем фабриками в `api/`-модуле фичи, а не строкой по месту вызова.

### Мутации

- Изменения через `useMutation` + `invalidateQueries` по префиксу ключа в `onSuccess`. Не дёргаем `refetch()` вручную и не правим состояние в обход кеша.
- Оптимистичные обновления — только когда это заметно улучшает UX, и обязательно с откатом в `onError` и `invalidateQueries` в `onSettled`.

### Состояния загрузки и ошибок

- Обрабатываем все три ветки: `isPending`, `error`, данные. Компонент, отрисовывающий только успех, считается незаконченным.
- `error` типизируем через свой класс ошибки, не приводим к `Error` кастом там, где можно объявить тип.
- Глобальные настройки повторов и `staleTime` — в `QueryClient` в одном месте, а не копипастой по хукам.

## Клиентское состояние — Zustand

**В Zustand не хранятся серверные данные.** Всё, что пришло из API, живёт в кеше Query; копия в сторе — типовой источник расхождений. В сторе только UI-состояние: фильтры, черновики форм, открытые модалки, шаги визарда, настройки отображения.

Сторов ещё нет — первый задаст конвенцию, поэтому пишем его аккуратно:

- Один стор на фичу, в `features/<feature>/model/<feature>.store.ts`. Один глобальный стор на всё приложение не заводим.
- Тип состояния объявляем явно, действия кладём внутрь стора рядом с данными:

```ts
interface FiltersState {
  city: string | null
  setCity: (city: string | null) => void
  reset: () => void
}

export const useFiltersStore = create<FiltersState>((set) => ({
  city: null,
  setCity: (city) => set({ city }),
  reset: () => set({ city: null }),
}))
```

- **Подписываемся селектором**, а не забираем стор целиком: `useFiltersStore((s) => s.city)`. `const store = useFiltersStore()` перерисовывает компонент на любое изменение.
- Селектор, возвращающий новый объект или массив, требует `useShallow`, иначе будет ререндер на каждый рендер.
- Действия вызываем через `useFiltersStore.getState().setCity(...)` вне React и через селектор внутри компонентов.
- Не держим в сторе то, что выводится из других значений, — считаем на месте или мемоизируем.

### Граница между Query и Zustand

| Что | Где |
|---|---|
| Данные из API, их загрузка, кеш, инвалидация | TanStack Query |
| Параметры запроса (фильтры, страница, поиск) | Zustand (или URL), затем передаются в ключ запроса |
| Черновик формы до отправки | Zustand или локальный `useState` |
| Результат отправки формы | Query (мутация + инвалидация) |
| Открыт ли диалог, выбранная вкладка | Zustand или локальный `useState` |

Локальный `useState` — нормальный ответ, если состояние не покидает компонент. Zustand заводим, когда состояние нужно нескольким несвязанным компонентам.

## Контракт с бэкендом

- Типы ответов не пишем руками — импортируем из `@flatnik/shared`. Если нужного типа там нет, значит на бэкенде нет DTO или не прогнана генерация: это правится на бэкенде (`npm run openapi` в корне), а не локальным интерфейсом во фронте.
- `shared` резолвится в `shared/dist`, поэтому после правки контракта его нужно пересобрать, иначе фронт видит старые типы.
- Ошибка компиляции после изменения контракта — это работающая защита, а не помеха. Чиним вызовы, а не глушим `as`/`@ts-ignore`.
- Пути эндпоинтов — из схемы; относительный `/api/...`, никаких хардкодов хоста и порта.

## Рендеринг и производительность

- Ключи списков — стабильный `id` из данных, не индекс массива.
- `useMemo`/`useCallback` — по факту заметной стоимости, а не превентивно.
- Не вызываем `setState` в `useEffect` для того, что можно вычислить при рендере.
- `React.StrictMode` включён: двойной вызов эффектов в dev — норма, эффекты должны быть идемпотентны и с очисткой.

## Проверки перед сдачей задачи

1. `npm run build --workspace=@flatnik/front` проходит: тайпчек и сборка.
2. Если менялся контракт — пересобран `shared`, типы во фронте актуальны.
3. Новый экран проверен в браузере на всех состояниях: загрузка, ошибка (можно погасить бэкенд), пустые данные, успех.
4. В консоли браузера нет предупреждений React (ключи, обновление состояния при размонтировании).
5. В диффе нет `console.log`, закомментированного кода и временных моков.

## Чего не делать

- Не грузить данные через `useEffect` + `fetch` в обход Query.
- Не дублировать серверные данные в Zustand.
- Не подписываться на стор целиком без селектора.
- Не писать типы API руками и не править `shared/src/api.generated.ts`.
- Не хардкодить адрес бэкенда: только относительный `/api/...`.
- Не добавлять UI-библиотеки, роутеры и прочие крупные зависимости без согласования — сейчас во фронте только React, Query и Zustand.
- Не заводить ESLint/Prettier/тесты походя: их в проекте нет, это отдельное решение.
